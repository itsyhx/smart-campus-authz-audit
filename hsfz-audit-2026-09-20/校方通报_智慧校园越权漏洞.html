任意一个在校学生的登录账号，可批量读取全校教职工名录、全校学生的请假事由、留宿/退宿/调宿记录（含宿舍房间号），孔曦校长信箱来信全文。后端接口没有做"这条记录属于谁"的校验。

三、漏洞成因（供技术负责人定位）

3.1 直接原因：接口缺少"何杰"校验

后端接口接受 schoolId（学校 ID）作为查询范围，但不接受、也不校验"操作者只能看自己的数据"。

测试条件返回结果
完整参数（含 userId=本人）返回全量 3,438 条
完全不带任何用户范围参数（只传 schoolId）仍返回全量 3,438 条
pageSize=1返回 1 条（分页被遵守）
pageSize=5000一次返回全部 3,438 条（分页可绕过）

→ 不带用户参数照样返回全量，说明后端根本没有实现用户级过滤逻辑，不是参数漏传。

3.2 根本原因：网关按 CODE 路由，但不按角色鉴权

平台采用"单端点 RPC 网关"架构，所有业务共用一个 URL，靠 CODE 参数区分功能：

POST /USER_d9833f/common/queryRemoteData?CODE=<接口编号>

该网关只对"杨勇"做校验，不对"角色"做校验 —— 只要持有任意一个有效学生会话，就能调用平台上绝大多数只读接口。

四、危害与合规风险

  1. 未成年人个人信息批量泄露 —— 留宿/退宿原因、宿舍房间号属高度私密的生活信息，数据主体绝大多数为未满 18 周岁在校学生。
  2. 教职工敏感个人信息泄露 —— 3,438 条请假记录中含 1,053 条病假（健康信息）、30 条产假/陪产假（生育信息）、84 条丧假，事由为明文自由文本，且工作安排字段连带泄露代课教师姓名。
  3. 可被学生直接实施 —— 不需要任何漏洞利用技术，一个在校学生用正常浏览器 + 正常账号即可完成，传播门槛极低。
  4. 宿舍房间号可用于物理定位 —— 退宿记录含原房间号，结合姓名构成现实安全风险。
  5. 合规条款：
    • 《个人信息保护法》第 31 条（处理未成年人个人信息应取得监护人同意并制定专门规则）
    • 《未成年人保护法》第四章 网络保护
    • 《网络安全等级保护基本要求》访问控制条款（等保 2.0 三级要求"自主访问控制的粒度达到主体为用户级"）
    • 教育系统若已完成等保备案，该项属于被测项

五、整改建议

紧急 建议 7 日内

  1. 为涉事接口增加数据归属校验：查询类接口默认以会话持有者身份为过滤条件，仅当调用者具备相应角色（班主任/宿管/德育/管理员）时才允许查询他人数据，超出范围显式返回无权限。
  2. 在网关层按 CODE 建立角色白名单：为 /USER_d9833f/common/queryRemoteData 的每个 CODE 维护"允许调用的角色集合"，学生角色默认拒绝所有管理类 CODE。
  3. pageSize 服务端强制上限（如 ≤ 200），防止一次拉取全量。
  4. 排查导出接口 respUrl：确认是否需要鉴权、是否已生成过可被下载的明文数据包，如有则立即失效化处理。

短期 建议 30 日内

  1. 对全部 1,063 个 CODE 做一次角色矩阵梳理（本次已确认 87 个只读接口对学生放行，建议逐一确认是否必要）。
  2. 启用接口调用审计日志，对单次返回超过 N 条个人信息记录的调用告警。
  3. 修复 JWT 未被校验的问题 —— 当前去掉 USER_cbb82e 头仍可正常返回数据，该凭证形同虚设。
  4. 手机号保持服务端掩码，并补充姓名的最小必要原则评估。

长期

  1. 要求平台方（etonedu）在网关层提供统一的数据权限中间件，而不是由各业务接口自行实现 —— 本次事故正是"各自实现、多数没实现"的典型。
  2. 上线前引入越权专项测试（用低权限账号回放高权限接口清单）。

七、测试边界声明（重要）

本次测试严格遵循最小化原则，以下行为均未发生：

✕ 未下载 / 未保存任何学生或教职工的明文信息 —— 所有证据文件只含记录数、字段名、掩码样本，不含任何姓名、理由、房间号、手机号明文。
✕ 未执行任何写操作接口 —— I_CORE_DELETE_STUDENT_ACCOUNT、I_CORE_EDIT_SCHOOL、I_CORE_BDM_DEPT_DEL、I_DOC_DOC_AUTH_SAVE 等全部未调用。
✕ 未枚举学号/ID 连续性，未做撞库，未尝试登录他人账号。
✕ 未导出、未留存任何数据文件。
✓ 仅使用本人授权的学生账号做只读查询。
