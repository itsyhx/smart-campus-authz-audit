## 二、方法与可信性保障

### 2.1 零写入原则

- 全部请求为**只读语义**（`LIST` / `PAGE` / `QUERY` / `SEARCH` / `EXPORT` / `DOWNLOAD` / `STAT`）
- 请求体**不携带任何业务主键**（无 id、无主键、无状态字段）
- 因此服务端即便放行，也**无法执行任何变更**

### 2.2 不记录数据内容

脚本只提取三项元信息：

- `rescode` —— 业务返回码
- `rows` —— 返回条数
- `fields` —— 字段**名**，且仅匹配预定义 PII 字段名单

**任何字段值都不落盘。**

### 2.3 对照组设计（可信性锚点）

| 孙娟 | 返回 | 金英 |
|---|---|---|
| `I_FAKE_CODE_ZZZ_999`（人为编造） | `90000 接口不存在` | 请求**已抵达网关业务层** |

`90000` 证明登录态校验已放行、请求真正进入 CODE 路由。

若返回 `403`，说明请求被拦在**会话层**，测试无效——这正是前次误判的原因。

## 四、结论

1. **鉴权层对上述 176 个候选接口的拦截数为 0。**
   返回码中没有出现任何一次 `403`，全部是「参数不足」（`12004`）、
   「服务异常」（`12001`）或「陶桂」（`10000`）。

2. **可达面 = 接口总数。**
   平台注册 1063 个 CODE，本次仅抽取 176 个高价值候选，其中 125 个已确认可达。
   结合前次 137 个只读接口复测（拦截数同样为 0），可判定网关鉴权逻辑
   **只校验登录态，不校验接口归属与角色**。

3. **根因**：会话 JWT 的 `menuPermission` 字段为 `["*:*:*"]`（通配全权限），
   服务端直接采信该声明。

4. **与「已修复」结论矛盾**：本次复测在会话有效（对照组返回 `90000`）的前提下，
   未观察到任何接口层面的鉴权收紧。

---

## 五、建议

1. **不要依赖前端菜单隐藏**——攻击面是接口，不是页面。
2. **网关层引入接口级白名单**：为每个 CODE 声明允许的角色集合，**默认拒绝**而非默认放行。
3. **修正 JWT 权限声明**：`menuPermission` 不应下发 `*:*:*`，应按角色下发具体权限项。
4. **新旧网关分别处理**：新网关 `/api/USER_429c64/USER_d9833f/*` 已有双层校验；
   旧网关 `/USER_d9833f/common/queryRemoteData` 仍是单端点 RPC，建议同等加固或整体下线。
5. **导出类接口单独加固**：`EXPORT` / `DOWNLOAD` 语义接口共 **69 个**，
   建议全部追加二次鉴权与操作留痕。
