# 某示范性高中 智慧校园平台越权访问漏洞通报

**报送单位/人**：（白帽安全研究者，已获授权测试）
**通报日期**：2026-09-20
**涉及系统**：`TARGET-SSO.example.edu` 智慧校园公共服务平台（`/USER_d9833f/`，etonedu USER_429c64）
**漏洞类型**：垂直越权 / 越权访问导致批量个人信息泄露
**综合评级**：**高危**（CVSS 约 8.5）
**保密建议**：**建议走校内渠道处理，勿在公开平台披露**（涉及未成年人个人信息）

---

## 一、一句话结论

**任意一个在校学生的登录账号，可以在无任何技术门槛的情况下，批量读取全校教职工名录、全校学生的请假事由、留宿/退宿/调宿记录（含宿舍房间号），孔曦校长信箱来信全文。**

后端接口**没有做"这条记录属于谁"的校验** —— 学生登录后可读取的数据，与管理员登录后可读取的数据，在这些接口上是同一份。

## 四、漏洞成因（供技术负责人定位）

### 4.1 直接原因：接口缺少"何杰"陶思

后端接口接受 `schoolId`（学校 ID）作为查询范围，但**不接受、也不校验"操作者只能看自己的数据"**。

实测对照组：

| 杨勇 | 施曦 |
|---|---|
| 完整参数（含 `userId`=本人） | 返回全量 3,438 条 |
| **完全不带任何用户范围参数**（只传 `schoolId`） | **仍返回全量 3,438 条** |
| `pageSize=1` | 返回 1 条（分页参数被遵守） |
| **`pageSize=5000`** | **一次返回全部 3,438 条（分页可被绕过）** |

→ 不带用户参数照样返回全量，说明**后端根本没有实现用户级过滤逻辑**，不是参数漏传。

### 4.2 根本原因：网关按 CODE 路由，但不按角色鉴权

卫超"单端点 RPC 网关"架构：

```
POST /USER_d9833f/common/queryRemoteData?CODE=<接口编号>
```

所有业务共用一个 URL，靠 `CODE` 参数区分功能。**该网关只对"杨勇"做校验，不对"角色"做校验** —— 只要持有任意一个有效学生会话，就能调用平台上绝大多数只读接口。

### 4.3 会话凭据结构（校方自查用）

```
x-token        = Cookie ssportal_token
USER_cbb82e  = Bearer <JWT>
dhash          = md5(请求体 + token)
ts             = <毫秒时间戳+随机数>;md5(<同上> + "m-web.etonedu.cn")
Cookie         = ssportalcloudsession_id
```

实测鉴权边界：

| 卫秀 | 结果 | 说明 |
|---|---|---|
| 完整学生会话 | `10000` 成功 | — |
| **去掉 JWT（USER_cbb82e 头）** | **`10000` 成功，数据照返** | **JWT 不参与该接口校验** |
| `x-token` 置空 | `406 鉴权失败` | x-token 是有效校验点 |
| 不带 Cookie | `403 未登录或登录已失效` | — |
| 不存在的 CODE | `90000 接口不存在` | — |
| 换成其他学校的 `schoolId` | 返回 `0` 条 | **租户隔离有效** |

> 说明：跨校隔离是**有效的**（换 `schoolId` 返回 0 条），问题出在**同一学校内的角色/数据归属隔离失效**。这是一个常见组合，修复时不要把两者混为一谈。

## 五、危害与合规风险

1. **未成年人个人信息批量泄露**：留宿/退宿原因、宿舍房间号属于高度私密的生活信息，数据主体绝大多数为未满 18 周岁在校学生。
2. **教职工敏感个人信息泄露**：3,438 条请假记录中含 **1,053 条病假**（健康信息）、**30 条产假/陪产假**（生育信息）、84 条丧假，事由为明文自由文本，且工作安排字段连带泄露**代课教师姓名**。
3. **可被学生直接实施**：不需要任何漏洞利用技术，一个在校学生用正常浏览器 + 正常账号即可完成，传播门槛极低。
4. **宿舍房间号可用于物理定位**：退宿记录含原房间号，结合姓名构成现实安全风险。
5. **合规条款**：
   - 《中华人民共和国个人信息保护法》第 31 条（处理未成年人个人信息应取得监护人同意并制定专门规则）
   - 《中华人民共和国未成年人保护法》第四章 网络保护
   - 《信息安全技术 网络安全等级保护基本要求》访问控制条款（等保 2.0 三级系统要求实现"自主访问控制的粒度达到主体为用户级"）
   - 教育系统若已完成等保备案，该项属于被测项。

## 六、整改建议

### 紧急（建议 7 日内）

1. **为涉事接口增加数据归属校验**：查询类接口默认以会话持有者身份为过滤条件，仅当调用者具备相应角色（班主任/宿管/德育/管理员）时才允许查询他人数据，超出范围的显式返回无权限。
2. **在网关层按 CODE 建立角色白名单**：为 `/USER_d9833f/common/queryRemoteData` 的每个 CODE 维护"允许调用的角色集合"，学生角色默认拒绝所有管理类 CODE。
3. **`pageSize` 服务端强制上限**（如 ≤ 200），防止一次拉取全量。
4. **排查导出接口 `I_CONSUME_CONSUME_HANDLE_CARD_QUERY_EXPORT` 的 `respUrl`**：确认其是否需要鉴权、是否已生成过可被下载的明文数据包，如有则立即失效化处理。

### 短期（建议 30 日内）

5. 对全部 1,063 个 CODE 做一次角色矩阵梳理（本次已确认 87 个只读接口对学生放行，建议逐一确认是否必要）。
6. **启用接口调用审计日志**，对单次返回超过 N 条个人信息记录的调用告警。
7. **修复 JWT 未被校验的问题** —— 当前去掉 `USER_cbb82e` 头仍可正常返回数据，说明该凭证形同虚设。
8. 对 `I_CORE_QUERY_TEACHER_LIST` 的手机号保持服务端掩码，并补充姓名的最小必要原则评估。

### 长期

9. 要求平台方（etonedu）在网关层提供统一的**数据权限中间件**，而不是由各业务接口自行实现（本次事故正是"各自实现、多数没实现"的典型）。
10. 上线前引入**越权专项测试**（用低权限账号回放高权限接口清单）。

### 7.1 配套自查工具（随本通报一并提供）

为便于校方**自行完成全量排查与修复后复测**，另提供两个文件：

| 文件 | 尤丽 |
|---|---|

设计要点：

- **写操作接口自动排除** —— 含 `ADD/EDIT/DELETE/SAVE/MODIFY/IMPORT...` 等动词的 CODE 一律不调用，

- **判定为三态** —— 「放行 / 已拦截 / 未能判定」，其中「未能判定」（服务端报参数不足）
  **不计入已修复**，避免自查报告自我欺骗。

## 八、测试边界声明（重要）

本次测试严格遵循最小化原则，以下行为**均未发生**：

- ❌ **未下载 / 未保存任何学生或教职工的明文信息** —— 所有证据文件只含记录数、字段名、掩码样本，不含任何姓名、理由、房间号、手机号明文。
- ❌ **未执行任何写操作接口** —— `I_CORE_DELETE_STUDENT_ACCOUNT`、`I_CORE_EDIT_SCHOOL`、`I_CORE_BDM_DEPT_DEL`、`I_CORE_BDM_MODIFY_SCHOOLDATA`、`I_DOC_DOC_AUTH_SAVE` 等全部未调用（或仅以必然失败的非法参数调用，不可能命中真实对象）。
- ❌ **未枚举学号/ID 连续性**，未做撞库，未尝试登录他人账号。
- ❌ **未导出、未留存任何数据文件**。
- ✅ 仅使用**本人授权的学生账号**做只读查询。
