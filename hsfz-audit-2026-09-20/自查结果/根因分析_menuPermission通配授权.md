## 一、发现

对 `TARGET-SSO.example.edu` 的 `auth_token`（HS256 JWT，payload 未验签即可读）做离线解析，
发现 **4 个学生账号**的权限声明如下：

| 账号 | userId | memberId | roleAlias | menuPermission | rolePermission |
|---|---|---|---|---|---|
| 沈静 | -3557096 | 5587790 | 1（学生） | `["*:*:*"]` | `["1"]` |
| 杨华 | -4527023 | 5579606 | 1（学生） | `["*:*:*"]` | `["1"]` |
| 陶建 | -4526864 | 5579751 | 1（学生） | `["*:*:*"]` | `["1"]` |
| 秦思 | **4660740** | 6582201 | 1（学生） | `["*:*:*"]` | `["1"]` |

**4 个账号的 `menuPermission` 全部是 `*:*:*` —— 通配全权限。**

### 一处值得注意的结构差异

前三个账号的 `userId` 为**负数**（`-3557096` / `-4527023` / `-4526864`），
第四个为**正数**（`4660740`），且 `memberId` 段位也不同（6582201 vs 55xxxxx）。

这说明：

- 平台内**存在两套 `userId` 命名空间**（正数 / 负数），可能对应不同的开户流程或数据来源；
- **`userId` 的正负号不能作为账号类型的判据** —— 第四个账号虽为正数 `userId`，
  `roleAlias` 仍为 `1`（学生），权限声明与其余三个完全一致。

进一步印证：权限缺陷与账号来源、开户渠道无关，**凡 `roleAlias=1` 一律获得 allow-all**。

原始 payload（账号一，节选）：

```json
{
  "loginType": "login",
  "loginId": "portal:5587790",
  "data": {
    "memberName": "沈静",
    "organizeId": 50656,
    "roleAlias": 1,
    "userId": -1903234,
    "menuPermission": ["*:*:*"],
    "rolePermission": ["1"]
  }
}
```

## 二、为什么这是根因

此前对现象的观察是：

- 137 个只读接口对学生会话可达
- 写接口穿过鉴权层（返回 `12004` 而非 `403`）
- 跨校区数据可读（某校区、五华、石牌）

**这三个现象共用一个解释。**

如果网关的授权判断读取 `menuPermission`，那么：

```
学生账号的 menuPermission = ["*:*:*"]
                          ↓
        等价于 allow-all（所有菜单、所有资源、所有操作）
                          ↓
        鉴权层对任何 CODE 都放行 —— 读接口、写接口一律无差别通过
```

`*:*:*` 是 `赵丽:韩宇:钱芳` 形式的通配符，三个位置全为 `*`，即：

| 章子 | 许勇 | 金英 |
|---|---|---|
| 赵丽 | `*` | 任意业务模块 |
| 韩宇 | `*` | 任意操作（含读、写、审批、导出） |
| 钱芳 | `*` | 任意数据范围（全校区、全年级） |

**一个只该拥有"查自己课表"权限的学生账号，声明里持有 allow-all。**

## 四、影响定级建议

**这是配置级缺陷，不是编码遗漏。**

- 修复面小：修正 `menuPermission` 的生成逻辑（按 roleAlias 映射），而非重写鉴权层
- 影响面大：**样本内 4/4 学生账号统一持有 `*:*:*`**（含正负两套 `userId` 命名空间），
  等于平台对学生角色无权限隔离
- 可验证：修复后重跑 `_写侧鉴权探测.py`，写接口应返回 `403`/`406`
