## 一、一句话结论

**任意一个在校学生的普通账号，不需要任何技术手段，就能批量读取全校教职工名录、全校教职工请假事由（含病假/产假）、全校学生的留宿/退宿/调宿记录（含宿舍房间号），孔曦校长信箱来信全文。**

原因不是学生"曹思"，而是后端**压根没有做"这条记录属于谁"的校验**——普通学生和管理员在这些接口上拿到的，是同一份数据。

## 三、漏洞根因（三句话讲清）

1. **网关只认"登录"，不认"角色"。** 平台所有业务共用一个接口 `POST /USER_d9833f/common/queryRemoteData?CODE=<功能编号>`，网关只校验"是否存在有效会话"，不校验"这个角色能不能调这个功能"。实测 539 个只读接口中 87 个对学生角色放行。
2. **接口不校验"数据属于谁"。** 实测对照：带本人条件返回 3,438 条；**完全不带任何用户范围参数，仍返回全量 3,438 条**；分页参数 `pageSize` 改大后**一次返回全量**。说明后端未实现用户级过滤，不是参数漏传。
3. **请求签名由前端可计算，且 JWT 不参与校验。** 网关的签名头由前端脚本生成（人人可得），实测去掉 JWT 凭证后接口照常返回数据——该凭证形同虚设。有效的校验点只有会话 Cookie 与 `x-token`。

**注意**：跨校租户隔离是**有效的**（换成其他学校 ID 返回 0 条）。问题出在**同一学校内部的角色/数据归属隔离缺失**。修复时不要把两者混为一谈。

## 四、为什么"现在登录不上"不影响本通报的结论

**本通报的全部数字来自 2026-09-20 当天的实测返回结果与对照实验，证据是当时的响应数据，不依赖"现在还能复现"。**

近期出现该地址/账号无法登录的情况，属正常现象，常见原因包括：

- 会话/令牌自然过期；
- 校方对账号执行了改密、停用或风控锁定（含失败次数锁定）；
- 访问入口网络策略调整；
- `/USER_d9833f/` 本身是网关基址而非登录页，直接在浏览器打开本就不会出现登录流程。

以上任何一种情况都**不构成"漏洞不存在"的证据**，也**不需要**报送人或校方重新登录才能开始修复——修复依据是本文档第三节的根因，与登录状态无关。

## 五、整改建议

### 紧急（建议 7 日内）

1. **为涉事接口增加数据归属校验**：查询类接口默认以会话持有者为过滤条件；仅当调用者具备相应角色（班主任/宿管/德育/管理员）时才允许查询他人数据，越界显式返回无权限。
2. **在网关层按 CODE 建立角色白名单**：为 `queryRemoteData` 的每个 CODE 维护"允许调用的角色集合"，学生角色默认拒绝全部管理类 CODE。
3. **`pageSize` 服务端强制上限**（如 ≤200），禁止一次拉取全量。
4. **排查导出接口**（`I_CONSUME_CONSUME_HANDLE_CARD_QUERY_EXPORT`）的 `respUrl`：确认是否需要鉴权、历史导出包是否仍可下载，如有则立即失效化。

### 短期（建议 30 日内）

5. 对全部 1,063 个 CODE 做角色矩阵梳理（本次已确认 87 个只读接口对学生放行，逐一确认是否必要）。
6. **启用接口调用审计日志**，对单次返回超过 N 条个人信息记录的调用告警。
7. **修复 JWT 未被校验的问题**——当前该凭证形同虚设。
8. 教职工名录的手机号保持服务端掩码，并按最小必要原则评估姓名字段是否应下发到学生端。

### 长期

9. 要求平台方（etonedu）在网关层提供统一的**数据权限中间件**，而不是各业务接口自行实现——本次事故正是"各自实现、多数没实现"的典型。
10. 上线流程引入**越权专项测试**（用低权限账号回放高权限接口清单）。

## 六、修复后如何验证（校方自查，零脚本）

1. 用**一个测试学生账号**（校方自建，勿用真实在校生）从正常页面登录。
2. 逐个打开涉及他人数据的功能：教师名录、请假管理、留宿/退宿/调宿管理、校长信箱。
3. **预期**：要么看不到该功能入口，要么只能看到该测试学生本人的记录（通常为空）。
4. **若仍能看到全校数据，说明未修复。**
5. 再用管理员账号重复以上操作，确认管理员功能未受影响。
6. 建议由平台厂商在网关层开启调用日志后复核一遍，确认低权限会话对这些 CODE 的调用被拒绝并留有审计记录。
